# DentMarket KZ: правила работы агентов и разработчиков

Этот файл обязателен для любой задачи в репозитории. Он не заменяет
продуктовое ТЗ или архитектурные ADR: он определяет, **как** безопасно
менять проект и как доказывать готовность результата.

## 1. Источники правды

При конфликте документов используйте следующий порядок:

1. `DENTMARKET_PRODUCT_V2.md` — целевой продукт, границы пилота и
   бизнес-правила.
2. `DENTMARKET_BACKEND_FOUNDATION_V2.md` — техническая последовательность
   работ и backend Definition of Done.
3. `docs/adr/` — уже принятые архитектурные решения.
4. Контракты в `packages/schemas`, API client и OpenAPI — исполняемое
   описание границы frontend/backend.
5. `PROJECT_ACCEPTANCE_MATRIX.md` — статус и доказательства; исторические
   записи не являются гарантией текущего состояния.

Код или старый документ не расширяет пилот автоматически. AI assistant,
trust/reputation, billing/tariffs и advanced recommendations остаются вне
пилота, пока Product V2 не будет изменён явным решением владельца продукта.

## 2. Карта репозитория

- `apps/api` — NestJS API, Prisma schema и доменная логика.
- `apps/buyer-web`, `apps/supplier-web`, `apps/admin-web` — Next.js кабинеты.
- `apps/landing-web` — публичные и маркетинговые страницы.
- `apps/e2e` — Playwright критических сценариев.
- `packages/schemas` — общие Zod-схемы и типы контрактов.
- `packages/api-client` — типизированный клиент core API.
- `packages/ui` — общие UI-примитивы на Fluent UI v9.
- `scripts` — обслуживающие и проверочные сценарии. Перед изменением или
  удалением скрипта проверьте его вызовы в `package.json`, CI и runbooks.

## 3. Обязательный маршрут задачи

1. Прочитайте релевантные Product V2, Foundation, ADR и кодовый маршрут.
2. Сформулируйте границу: пользователь, сценарий, входы, ожидаемый выход,
   ограничения и Definition of Done. Не начинайте код с неясным результатом.
3. Для изменения доменных данных или HTTP API сначала измените общую схему и
   контракт, затем реализацию и клиент, затем интерфейс.
4. Делайте минимальный связный change set. Не смешивайте рефакторинг,
   редизайн, удаление данных и новую бизнес-функцию в одном коммите.
5. Добавьте или обновите тест на риск, который устраняет задача.
6. Выполните проверки из `docs/DEVELOPMENT_WORKFLOW.md`, соответствующие
   затронутой области.
7. Обновите документацию, если изменились контракт, бизнес-правило, команда,
   эксплуатационный процесс или архитектурное решение.
8. Перед коммитом проверьте `git diff --check`, рабочее дерево и состав
   staged-файлов. В финале сообщайте фактические команды и результаты, а не
   предполагаемый статус.

## 4. Backend и данные

- Сохраняйте modular monolith. Не выделяйте микросервис без независимого
  владения, развёртывания или масштабирования.
- Любое изменение Prisma schema требует migration, `prisma validate` и
  проверки upgrade-path. Не редактируйте применённые migration-файлы.
- Каждая запись и чтение с организационными данными проверяет tenant context и
  разрешение до обращения к данным. Нельзя принимать tenant/actor из
  недоверенного заголовка как источник авторизации.
- Деньги храните в minor units; не используйте JavaScript `number` для
  точных денежных вычислений. Проверяйте инварианты в транзакции.
- Внешние вызовы, checkout, резервы и webhooks должны иметь идемпотентность и
  контролируемую компенсацию. Не выдавайте успех до фиксации нужной транзакции.
- Изменение цены, остатка или доступности обязано проходить revalidation перед
  checkout. Интерфейс обязан показать пользователю существенный diff до
  подтверждения новой версии.
- Seed-данные не являются бизнес-логикой. До B0.5 не смешивайте новые demo,
  test и pilot fixtures в монолитный seed без отдельного обоснования.

## 5. Контракты API

- Новая или изменённая core-операция начинается с Zod-схемы в
  `packages/schemas` и явных request/response/error типов.
- Обновляйте OpenAPI и `@marketplace/api-client` вместе с сервером; не
  дублируйте незадокументированные DTO в Next.js приложениях.
- Сохраняйте безопасный error envelope (`code`, `requestId`, `path`,
  `details`). Ошибки не должны раскрывать секреты, SQL или внутренние токены.
- Для write-операции укажите авторизацию, validation, conflict semantics,
  идемпотентность и audit/outbox effect там, где они применимы.

## 6. Frontend, UI и UX

Полный стандарт находится в `docs/UI_UX_IMPLEMENTATION_STANDARD.md`.

- Кабинеты покупателя, поставщика и оператора используют Fluent UI v9 и
  общие примитивы из `packages/ui`. Не вводите второй design system или
  библиотеку иконок для одной страницы.
- Любая асинхронная поверхность имеет loading, empty, error и success/action
  feedback состояния. Ошибка должна объяснять действие пользователя, а не
  только технический текст.
- Формы доступны с клавиатуры, имеют label, видимый focus, валидацию около
  поля и не теряют введённые данные при recoverable ошибке.
- Для плотных рабочих экранов приоритетны ясная иерархия, фильтры, таблицы,
  статусы и адаптивность, а не декоративная анимация.
- Не увеличивайте существующие очень большие route-файлы. Новую логику
  выносите в feature-компоненты, hooks, сервисы или pure utilities с тестами.
- Публичный landing может применять принципы Taste Skill только как
  арт-дирекцию. Они не отменяют доступность, существующую IA, SEO, аналитику
  или бренд. Не копируйте чужие SKILL.md и не применяйте маркетинговые паттерны
  к кабинетам.

## 7. Проверки

Базовый минимум для любого TypeScript change:

```powershell
pnpm typecheck
pnpm test
git diff --check
```

Дополнительно выбирайте проверку по риску, а не по удобству:

- контракт покупки — `pnpm verify:core-contract`;
- checkout, tenant isolation, rollback или конкурентный остаток —
  `pnpm verify:postgres`;
- runtime API/worker — `pnpm verify:runtime-split`;
- production environment — `pnpm verify:production-config`;
- затронутый UI critical flow — `pnpm verify:web` после запуска требуемого
  окружения;
- релизная готовность — `pnpm verify:release`.

Не ставьте `[x]` в планах и документации, пока проверка реально не прошла и
её результат не зафиксирован.

## 8. Git и безопасность

- Перед работой смотрите `git status --short --branch` и сохраняйте чужие
  незакоммиченные изменения.
- Одна логическая задача — один понятный conventional commit
  (`feat:`, `fix:`, `test:`, `docs:`, `refactor:`, `chore:`).
- Не используйте `git reset --hard`, принудительный push, удаление данных или
  production migration без явной задачи и проверки точной цели.
- Секреты, `.env`, production URLs, customer data и реальные ключи не
  попадают в git, логи, фикстуры или ответы.
- Push в ветку сам по себе не доказывает CI: убедитесь, что workflow настроен
  на эту ветку или откройте PR в ветку, на которой CI запускается.

## 9. Формат завершения задачи

В конце сообщите кратко: что изменено, какие пользовательские/технические
инварианты теперь обеспечены, какие команды прошли, что не запускалось и
почему, commit hash и branch. Не называйте работу завершённой при известном
непроверенном критическом риске.

## 10. Обязательные project playbooks

Для **каждой** задачи исполнитель использует этот `AGENTS.md` и
`docs/DEVELOPMENT_WORKFLOW.md`. Если затронут интерфейс, дополнительно
обязателен `docs/UI_UX_IMPLEMENTATION_STANDARD.md`.

Внешние материалы являются обязательным набором профессиональных практик, а
не набором инструкций, которые нужно бездумно складывать в один prompt:

- `C:\Users\user\Desktop\agency-agents-main\agency-agents-main` — выбирайте
  релевантные роли: backend architect для модели/границ, frontend developer
  для реализации, UI designer и UX architect для интерфейса, code reviewer
  для рисков, Git workflow master для истории, testing roles для доказательств.
- `Leonxlnx/taste-skill` — применяйте его brief-first и anti-generic подход к
  публичным страницам, landing и visual redesign. Не используйте его как
  дизайн-систему для B2B-кабинетов, data tables или сложных форм.

В task report укажите, какие роли/практики были применены и почему. Нельзя
объявлять использование роли или skill, если соответствующий чек-лист или
инструкция фактически не были прочитаны и применены.
