# DentMarket KZ: правила работы агентов и разработчиков

Этот файл обязателен для любой задачи в репозитории. Он не заменяет
продуктовое ТЗ или архитектурные ADR: он определяет, **как** безопасно
менять проект и как доказывать готовность результата.

Правила актуализированы 2026-09-14. Главный принцип: **одна согласованная
задача → минимальное изменение → достаточные проверки → остановка**.
Наличие backlog, skill или команды в runbook само по себе не разрешает её выполнять.

## Единственная рабочая папка — решение владельца 2026-09-21

- Код Platforma.Market изменяется только в
  `C:\Users\user\Desktop\dentmarket-kz-main`. До записи проверить фактический
  корень репозитория, ветку, HEAD, dirty files и владельца текущей задачи.
- Не создавать и не использовать другие worktrees, клоны и копии для разработки.
  Старые деревья — только read-only источники консолидации/восстановления до
  отдельной приёмки и уборки. Это отменяет прежнее правило отдельного clean worktree.
- На весь репозиторий один активный изменяющий исполнитель, включая контракты,
  миграции и общие документы. Параллельный аудит только read-only по названному
  снимку. Неожиданные правки другого исполнителя — остановка записи и сверка.
- Сохранять пользовательские изменения. Не переключать грязный checkout;
  изменение ветки только в согласованной Git-операции. Ветка не требует новой папки.
- Dev API/frontend/workers запускаются из этой папки; проверять источник
  процесса и профиль, а не только localhost. Не останавливать чужие процессы.
  Изолированные тестовые БД и generated build artifacts допустимы, но не являются
  альтернативным исходным кодом и не разрешают изменения рабочей БД.
- Commit/push выполняются по постоянному разрешению из §8 после проверок.
  Изменение рабочих данных и удаление деревьев требуют отдельного scope.
  Само правило не является технической блокировкой.
- Состояние консолидации и владелец:
  `actual_docs/governance/task-state/CONSOLIDATION-2026-09-21.md`.

### Обязательное восстановление контекста

При старте, возобновлении и после сжатия прочитать раздел «Сохранение контекста
и передача задачи» в `actual_docs/governance/DEVELOPMENT_WORKFLOW.md` и checkpoint
выбранной задачи. Сверить checkout, branch, HEAD, dirty scope и evidence до правок.
В многошаговой работе обновлять checkpoint без напоминаний пользователя;
строгий read-only по-прежнему запрещает файловые записи. Один scope — один
активный владелец. Не повторять завершённое, не сбрасывать попытки проверок и
не расширять последний разрешённый scope. Сжатие не разрешает commit/push,
новую продуктовую фазу или worktrees. Уточнение владельца 2026-09-21 отменяет
немедленную ротацию: приближение к концу окна и фактическое сжатие не прерывают
текущую задачу. Тот же исполнитель восстанавливает checkpoint и доводит весь
согласованный DoD до завершения. Только после обязательных checks/review,
согласованной публикации и фактического CI (если входят в DoD), завершения всех
операций и проверки понимания преемника разрешены передача и архивация по
`actual_docs/governance/SESSION_ROLLOVER.md`. FAIL/BLOCKED/PENDING/неизвестное
состояние не являются завершением: сохранить checkpoint и остановиться по
лимитам, без автоматической ротации. Нельзя урезать задачу до одного теста или
управляющей правки ради передачи. Аварийное восстановление уже прерванной
передачи требует явного решения владельца. При старте читать
`actual_docs/PROJECT_HANDOFF.md`, `.codex/project-session.json` и
`actual_docs/governance/task-state/PRIMARY-SESSION.md`. До архивации нужны
checkpoint полного результата, read-only comprehension преемника и остановка
старого писателя. После подтверждённого архива заранее проверенный преемник
или уполномоченный оркестратор идемпотентно завершает тот же переход; один
флаг реестра не доказывает ни готовность, ни архивирование.
Не-primary/retired задачи не начинают продуктовую запись и не создают новых
преемников. Для hook требуется отдельный review/trust, не обходить его.

## 1. Источники правды

При конфликте документов используйте следующий порядок:

1. `actual_docs/product/DENTMARKET_PRODUCT_V2.md` — целевой продукт, границы пилота и
   бизнес-правила.
2. `actual_docs/backend/DENTMARKET_BACKEND_FOUNDATION_V2.md` — техническая последовательность
   работ и backend Definition of Done.
3. `actual_docs/architecture/adr/` — уже принятые архитектурные решения.
4. Контракты в `packages/schemas`, API client и OpenAPI — исполняемое
   описание границы frontend/backend.
5. `actual_docs/governance/PROJECT_ACCEPTANCE_MATRIX.md` — статус и доказательства; исторические
   записи не являются гарантией текущего состояния.

Product определяет «что», этот файл и Development Workflow — «как».
Для запуска проверок, лимитов попыток и повторного использования evidence
каноничен Workflow; runbooks описывают отдельные процедуры, не новую очередь.
История и старые task cards не отменяют последнее явное решение пользователя.

Текущий продуктовый scope: внутреннее ядро CORE-01–09 без новых внешних
интеграций. POST-BE и POST-FULL — отложенная приёмка, EXT — отдельное разрешение.
По Product V2 §5.2 / ADR 011 пять дополнительных блоков разрешены в **локальном**
go_live; ограниченный pilot сохраняется. Это не разрешение реализовать все
заготовки AI/trust/promotions/billing/recommendations или запускать production.
Договор площадка–поставщик обязателен до публикации товаров.

## 3. Обязательный маршрут задачи

1. Проверьте Git, прочитайте эти правила, Workflow, релевантные Product V2,
   Foundation, ADR и кодовый маршрут. Не перечитывайте весь архив на каждом шаге.
2. Сформулируйте границу: пользователь, сценарий, входы, ожидаемый выход,
   ограничения, ID принятой задачи и Definition of Done. Укажите точные gates,
   окружение/fixtures и критерий остановки. Для короткой задачи достаточно
   краткого brief; новый файл ТЗ и повторное согласование уже ясного запроса не нужны.
3. Для изменения доменных данных или HTTP API сначала измените общую схему и
   контракт, затем реализацию и клиент, затем интерфейс.
4. Делайте минимальный связный change set. Не смешивайте рефакторинг,
   редизайн, удаление данных и новую бизнес-функцию в одном коммите.
5. Добавьте или обновите тест на риск, который устраняет задача.
6. Выполните проверки из `actual_docs/governance/DEVELOPMENT_WORKFLOW.md`, соответствующие
   затронутой области.
7. Обновите документацию, если изменились контракт, бизнес-правило, команда,
   эксплуатационный процесс или архитектурное решение.
8. Перед коммитом проверьте `git diff --check`, рабочее дерево и состав
   staged-файлов. В финале сообщайте фактические команды и результаты, а не
   предполагаемый статус.

### 3.1 Граница исполнения

- Выполняйте последний запрос, не накопленный список прежних «продолжай».
  «Продолжай» относится к текущей карточке/явно разрешённой последовательности,
  а не ко всем незакрытым чекбоксам. Новый запрос на аудит правил не запускает backend.
- Сначала проверьте существующие код, контракт и тест: если outcome уже
  реализован, добавьте только недостающее доказательство/исправление, не rewrite.
- Новая функция, интеграция, зависимость, смена стека, редизайн, массовая чистка
  или инфраструктура требуют основания в задаче. «Можно улучшить» не основание.
- Сторонний дефект фиксируйте один раз в существующей карточке/Acceptance Matrix.
  Не превращайте его в автоматический follow-up. Критический риск сообщите,
  остановите затронутый путь; не расширяйте молча scope.
- Не создавайте агентов/новые задачи без явного запроса на делегирование.
  Название роли Agency не означает поручение запускать отдельного агента.
- При достигнутом DoD завершите задачу. Следующую фазу начинайте только в явно
  разрешённой последовательности и после зелёных обязательных gates текущей.

## 4. Backend и данные

- Сохраняйте modular monolith. Не выделяйте микросервис без независимого
  владения, развёртывания или масштабирования.
- Любое изменение Prisma schema требует migration, `prisma validate` и
  проверки upgrade-path. Не редактируйте применённые migration-файлы.
- Каждая запись и чтение с организационными данными проверяет tenant context и
  разрешение до обращения к данным. Нельзя принимать tenant/actor из
  недоверенного заголовка как источник авторизации.
- Деньги храните в minor units; не используйте JavaScript `number` для
  точных денежных вычислений. Проверяйте инварианты в транзакции.
- Внешние вызовы, checkout, резервы и webhooks должны иметь идемпотентность и
  контролируемую компенсацию. Не выдавайте успех до фиксации нужной транзакции.
- Изменение цены, остатка или доступности обязано проходить revalidation перед
  checkout. Интерфейс обязан показать пользователю существенный diff до
  подтверждения новой версии.
- Seed-данные не являются бизнес-логикой. Используйте существующие отдельные
  reference/operator/pilot/test profiles. Проверки с записями выполняйте только
  на проверенной disposable test DB; не reseed рабочий demo-каталог ради зелёного теста.

## 5. Контракты API

- Новая или изменённая core-операция начинается с Zod-схемы в
  `packages/schemas` и явных request/response/error типов.
- Обновляйте OpenAPI и `@marketplace/api-client` вместе с сервером; не
  дублируйте незадокументированные DTO в Next.js приложениях.
- Сохраняйте безопасный error envelope (`code`, `requestId`, `path`,
  `details`). Ошибки не должны раскрывать секреты, SQL или внутренние токены.
- Для write-операции укажите авторизацию, validation, conflict semantics,
  идемпотентность и audit/outbox effect там, где они применимы.

## 6. Frontend, UI и UX

Полный стандарт находится в `actual_docs/ui-ux/UI_UX_IMPLEMENTATION_STANDARD.md`.

- Кабинеты покупателя, поставщика и оператора используют Fluent UI v9 и
  общие примитивы из `packages/ui`. Не вводите второй design system или
  библиотеку иконок для одной страницы.
- Любая асинхронная поверхность имеет loading, empty, error и success/action
  feedback состояния. Ошибка должна объяснять действие пользователя, а не
  только технический текст.
- Формы доступны с клавиатуры, имеют label, видимый focus, валидацию около
  поля и не теряют введённые данные при recoverable ошибке.
- Для плотных рабочих экранов приоритетны ясная иерархия, фильтры, таблицы,
  статусы и адаптивность, а не декоративная анимация.
- Не увеличивайте существующие очень большие route-файлы. Новую логику
  выносите в feature-компоненты, hooks, сервисы или pure utilities с тестами.
- Публичный landing может применять принципы Taste Skill только как
  арт-дирекцию. Они не отменяют доступность, существующую IA, SEO, аналитику
  или бренд. Не копируйте чужие SKILL.md и не применяйте маркетинговые паттерны
  к кабинетам.

## 7. Проверки

Базовый минимум для любого TypeScript change:

```powershell
npm run typecheck
npm test
git diff --check
```

Дополнительно выбирайте проверку по риску, а не по удобству:

- контракт покупки — `npm run verify:core-contract`;
- checkout, tenant isolation, rollback или конкурентный остаток —
  `npm run verify:postgres`;
- runtime API/worker — `npm run verify:runtime-split`;
- production environment — `npm run verify:production-config`;
- затронутый UI critical flow — `npm run verify:web` после запуска требуемого
  окружения;
- релизная готовность — `npm run verify:release`.

Docs-only: ссылки/согласованность правил, сохранность истории и `git diff --check`;
не запускать TS/build/DB/browser/security suites без соответствующего изменения.

Не ставьте `[x]` без фактического pass выбранного gate. Успешная проверка
переиспользуется для тех же входов по Workflow §4.2; истечение времени или
новый чат сами по себе не требуют полного rerun. Исторический pass без
проверяемых входов не сертифицирует новый checkout.

### 7.1 Защита от циклов

- До команды: зачем она нужна, какие входы/профиль проверяет, что изменилось
  после прошлого запуска. Если нового основания нет — не повторять.
- Максимум **3 попытки на один gate/блокер** (первичная + 2 с обоснованием),
  включая другие CLI/браузеры и новые сессии. Смена инструмента не сбрасывает счётчик.
- При одинаковом сбое без новой гипотезы остановитесь раньше лимита. Третья
  неуспешная попытка или исчерпанный time budget → blocked, отчёт и один следующий
  точный шаг; это не pass и не разрешение пропустить обязательную проверку.
- Полная сборка/тестовый набор не повторяются после docs-only правки, чтения
  логов, смены заголовка задачи или оформления коммита. Повторяется только
  проверка, входы которой действительно изменились.
- Ошибка инструмента/сессии не является доказательством дефекта приложения.
  Не обходите permissions, auth, CSP, freshness или ограничения файлов ради теста.
- Таймауты, журнал запусков, preflight и cleanup — Workflow §4.1–4.4.
  Эти правила ограничивают работу исполнителя, не меняют retries бизнес-очередей.

## 8. Git и безопасность

- Согласованная владельцем цель: `origin`
  (`https://github.com/NikIg228/dentmarket_04.08.git`), ветка `main`.
- Перед работой смотрите `git status --short --branch` и сохраняйте чужие
  незакоммиченные изменения.
- Одна логическая задача — один понятный conventional commit
  (`feat:`, `fix:`, `test:`, `docs:`, `refactor:`, `chore:`).
- Решение владельца 2026-09-21: после каждой разрешённой задачи реализации
  или документации, review её состава и PASS обязательных gates сразу сделать
  понятный commit и обычный push в согласованную remote/ветку. Это постоянное
  разрешение: повторно спрашивать о каждом push не требуется. Read-only и явное
  «без commit/push» имеют приоритет. Точный порядок — Workflow §5.1.
- Перед staging отделить собственный scope от чужого/незавершённого WIP,
  проверить весь outgoing range, секреты и приватные данные. Добавлять только
  проверенные пути/hunks; не использовать бездумный `git add .`.
- До push получить актуальный remote и проверить fast-forward. Неизвестная
  целевая ветка, конфликт, несвязанная история, failed gate или параллельная
  запись блокируют публикацию; не выбирать main и не сливать чужой код молча.
- После push сверить remote SHA с ожидаемым локальным commit и отдельно CI.
  При ошибке сохранить commit и сообщить «локально закоммичено, не отправлено».
  Новые PR, release/tag/deploy и рабочие миграции этим правилом не разрешаются.
- npm — выбранный package manager. Не возвращайтесь к выбору npm/pnpm и не
  меняйте lockfiles в несвязанной задаче; остаточный housekeeping имеет свой scope.
- Не используйте `git reset --hard`, принудительный push, удаление данных или
  production migration без явной задачи и проверки точной цели.
- Секреты, `.env`, production URLs, customer data и реальные ключи не
  попадают в git, логи, фикстуры или ответы.
- Push в ветку сам по себе не доказывает CI: проверить запуск и результат.
  Если CI не настроен на ветку — сообщить NOT_RUN, не открывать PR и не менять
  workflow без соответствующего запроса. Pending CI не означает PASS.

## 9. Формат завершения задачи

В конце сообщите кратко: что изменено, какие пользовательские/технические
инварианты теперь обеспечены, какие команды прошли, что не запускалось и
почему, commit hash и branch. Не называйте работу завершённой при известном
непроверенном критическом риске.

Для незавершённой задачи укажите конкретный блокер, число попыток и один
следующий шаг. После прерывания/смены контекста продолжайте с этого checkpoint,
сначала проверив изменившиеся входы; не начинайте весь аудит или набор команд заново.

## 10. Обязательные project playbooks

Для **каждой** задачи исполнитель использует этот `AGENTS.md` и
`actual_docs/governance/DEVELOPMENT_WORKFLOW.md`. Если затронут интерфейс,
дополнительно обязателен
`actual_docs/ui-ux/UI_UX_IMPLEMENTATION_STANDARD.md`.

Внешние материалы являются обязательным набором профессиональных практик, а
не набором инструкций, которые нужно бездумно складывать в один prompt:

- `C:\Users\user\Desktop\Agentic Skills\agency-agents-main` — выбирайте
  релевантные роли: backend architect для модели/границ, frontend developer
  для реализации, UI designer и UX architect для интерфейса, code reviewer
  для рисков, Git workflow master для истории, testing roles для доказательств.
- `Leonxlnx/taste-skill` — применяйте его brief-first и anti-generic подход к
  публичным страницам, landing и visual redesign. Не используйте его как
  дизайн-систему для B2B-кабинетов, data tables или сложных форм.

В task report укажите, какие роли/практики были применены и почему. Нельзя
объявлять использование роли или skill, если соответствующий чек-лист или
инструкция фактически не были прочитаны и применены.

прочитайте инструкцию полностью; повторное чтение неизменённой инструкции
