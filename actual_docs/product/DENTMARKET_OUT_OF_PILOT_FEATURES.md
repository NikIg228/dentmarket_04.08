# DentMarket KZ — свод скрытых внепилотных функций

Дата сверки: 2026-09-13. Кодовая база: `b259b10e4b3d2e1572e2e4eea1b2ae2709037a96`.
Назначение: быстро понять, что отключено в controlled pilot, что сохранено и
что потребуется перед включением. Это справочный документ, а не новое решение
о расширении продукта: приоритет остаётся у [Product V2](DENTMARKET_PRODUCT_V2.md).

## 1. Главное

В профиле `pilot` отключены **пять функциональных блоков**: AI, trust/reviews,
promotions, billing и smart recommendations. Их код сохранён, но соответствующие
Nest modules не входят в активный граф приложения. Существующие UI-панели
скрыты, а общий API client блокирует обращения к этим блокам до отправки в сеть.

Это **не удаление кода или данных** и **не подтверждение готовности этих функций
к запуску**. Пилот сосредоточен на закупке: найти товар → сравнить поставщиков →
собрать корзину → подтвердить изменения цены/остатка → оформить и исполнить
заказ → получить документы.

## 3. Как это выглядит по ролям

### Клиника — Buyer

- В меню «Сервисы» нет AI-помощника и smart-рекомендаций; поддержка и «О DentMarket» остаются.
- Каталог не показывает промо-блок и агрегаты отзывов.
- В сравнении поставщиков нет trust score и заглушки «Нет истории»; колонка называется «Документы».
- Не загружаются рейтинги и отзывы через `/trust` при открытии сравнения.
- В исполненном заказе отсутствует форма «Оставить отзыв».
- Базовое сравнение предложений продолжает работать. Метка «Рекомендуем» у
  первого предложения может сохраняться: это существующее ранжирование по
  коммерческим условиям, а не smart recommendations API или платное размещение.
  В pilot trust score в это ранжирование не передаётся.

Источники: [Buyer workspace](../../apps/buyer-web/app/page.tsx),
[меню сервисов](../../apps/buyer-web/app/buyer-services-menu.tsx),
[панель сервисов](../../apps/buyer-web/app/buyer-services-panel.tsx),
[заказы](../../apps/buyer-web/app/features/purchasing/buyer-orders.tsx),
[базовое ранжирование](../../apps/buyer-web/app/catalog-ranking.ts).

### Поставщик — Supplier

- В меню «Ещё» нет «Акции» и «Доверие и география»; их панели не монтируются.
- «Комплаенс» остаётся: документы и проверки организации не являются trust score.
- Скрытие объединённой trust-панели не удаляет core API адресов и складов.
  Это не обещание, что каждый элемент прежней панели перенесён на отдельный экран.

Источник: [Supplier workspace](../../apps/supplier-web/app/page.tsx).

### Оператор — Admin

- Раздел называется «Контроль и аудит», а не «Контроль и доверие».
- Trust operations с рейтингами и инцидентами не монтируется.
- Журнал оператора, фильтры истории и аудит изменений сохраняются.

Источник: [Admin workspace](../../apps/admin-web/app/page.tsx).
Landing также получает общий профиль при сборке; отдельного интерфейса этих
пяти блоков на публичных страницах в данном change set не добавляли.

## 4. Что отключение НЕ затрагивает

- Каталог, поиск, карточки, обычное сравнение предложений и цены поставщиков.
- Корзину, reprice, подтверждение изменившейся цены/остатка и checkout.
- Разделение заказа по поставщикам, подтверждение, отгрузку и статусы.
- Базовый платёжный процесс заказа и связанные документы. **Billing платформы
  — не оплата стоматологических товаров.** Готовность live PSP проверяется отдельно.
- Документолог: архив, загрузку и получение документов с проверкой доступа.
  Скрытый billing не превращает документолог в бухгалтерскую систему и не
  отменяет отдельные требования к реальным ЭЦП/ЭДО-интеграциям.
- Compliance и проверку документов, tenant isolation, permissions, безопасность.
- Geo/address, закупочные бюджеты, поддержку, уведомления и аудит.

Доступность core-модуля не равна подтверждённой работе его внешнего провайдера.
Live email, платежи, ЭЦП и инфраструктура не становятся готовыми от смены профиля.

## 5. Как работает отключение

1. **Backend:** `DEPLOYMENT_PROFILE=pilot` не включает пять optional modules.
   Произвольный вызов URL не добавляет отсутствующий controller в приложение.
2. **Frontend:** четыре Next.js приложения получают публичное значение профиля
   из `DEPLOYMENT_PROFILE` при сборке; панели и связанные загрузки условные.
3. **API client:** `MarketplaceApiClient` проверяет префикс до `fetch` для
   запросов чтения/изменения и скачивания. При запрете создаётся локальная ошибка
   `FEATURE_UNAVAILABLE` со статусом `404`; HTTP-запрос не отправляется.
4. **Конфигурация:** отсутствие профиля выбирает `pilot`. Неизвестный профиль
   или конфликт с `NEXT_PUBLIC_DEPLOYMENT_PROFILE` отклоняется Next config.
   Публичный флаг сам по себе не разрешает `go_live`.

Источник: [frontend profile contract](../../packages/schemas/src/deployment-profile.ts),
[API client](../../packages/api-client/src/index.ts),
[ADR 009](../architecture/adr/009-deployment-profile-composition.md),
[ADR 010](../architecture/adr/010-frontend-deployment-profile.md).

Важно: frontend не опрашивает API для автоматического переключения профиля.
Web builds и API должны быть развёрнуты с согласованной конфигурацией.
Изменение env после сборки не переписывает браузерный bundle: нужны rebuild
и перезапуск. Это профиль всего развёртывания, а не настройка отдельной клиники.

Сейчас все пять frontend flags вычисляются вместе: `pilot` → выключены,
`go_live` → включены. Отдельного разрешения «включить только отзывы в pilot»
этот механизм не предоставляет. Смена профиля не отменяет permissions и
дополнительные проверки внутри функций.

## 6. Другие функции вне пилота — отдельная категория

В Product V2 также исключены автоматические payouts, несколько PSP,
полноценный 1С Agent, OCR произвольных документов, бухгалтерские проводки и
налоговая отчётность, автоматические ЭСФ/СНТ без отдельного решения, внешняя
проверка государственных реестров, сложная лояльность, масштабирование на все
категории/регионы и микросервисная декомпозиция.

**Этот список нельзя считать перечнем функций, выключенных пятью flags выше.**
Это продуктовые ограничения. Кодовые заготовки или отдельные интеграционные
маршруты могут существовать; их полнота, доступность и готовность требуют
отдельной сверки. В частности, 1С foundation не равен готовому полноценному 1С Agent.

## 7. Что потребуется перед включением

Ниже будущие условия допуска, а не задачи, выполненные этим сводом:

- [ ] Владелец продукта явно утверждает расширение scope в Product V2.
- [ ] Для выбранного блока согласованы сценарий, бизнес-правила и Definition of Done.
- [ ] Проверена его собственная полнота: положительные и отрицательные сценарии,
      tenant/permission boundaries, ошибки и восстановление после сбоев.
- [ ] При необходимости подтверждены права на данные, модерация, тарифные и
      денежные правила, внешние провайдеры и эксплуатационная поддержка.
- [ ] Утверждён состав развёртывания. Нельзя молча включать все пять блоков
      через `go_live`, если согласован только один; точечное включение требует
      отдельного архитектурного решения и изменения механизма flags.
- [ ] Выполнены согласованные build/config/backend/browser gates в целевом
      профиле и подготовлен план отката к согласованному pilot release.
- [ ] Перед production выполнены отдельные production/live-evidence gates.

Эксплуатационная политика ADR 009 требует явный `go_live` для production;
это **не разрешение расширить продуктовый пилот**. При сверке обнаружено важное
различие политики и реализации: [environment.ts](../../apps/api/src/platform/config/environment.ts)
не запрещает сочетание production + pilot само по себе, а часть проверок
(например, строгие CORS, MFA и TLS PostgreSQL/Redis) находится внутри условия
production + go_live. Поэтому production-hosted pilot нельзя считать проверенным
только на основании успешного запуска или локальных pilot tests. Перед таким
развёртыванием нужна отдельная сверка и согласование обязательных safety gates
независимо от набора бизнес-функций. В рамках данного свода код не изменяется.

Порядок сборки и проверки: [deployment profiles runbook](../operations/deployment-profiles.md).
Рекомендация: держать эти блоки вне пилота до стабилизации основного закупочного
цикла; возвращать по одному утверждённому сценарию с отдельными доказательствами.

## 8. На чём основан статус

Предыдущая реализация на `b259b10` имеет локальное evidence в ADR 010:
typecheck 15/15, unit tasks 14/14, build tasks 10/10 с четырьмя web builds,
frontend config 4/4 и Playwright 23/23. Шесть новых browser cases проверяли три
роли на 1280/390 px, отсутствие optional requests и соответствие pilot OpenAPI.
Backend inventory: pilot — 36 modules / 224 routes; go_live — 41 / 257.

Эти результаты доказывают границу пилота, **не полную production-готовность
отключённых функций**. В задаче подготовки данного свода код не менялся,
runtime-тесты повторно не запускались; проверены соответствие исходникам,
локальные ссылки и Markdown diff. Статусы CI/deployment этим документом не повышаются.

Применены AGENTS.md, Development Workflow и Agency Backend Architect:
сверка границ модулей и API, сохранение закупочного ядра, отделение фактической
доступности от продуктового scope и доказательств готовности. UI/UX не менялся.
