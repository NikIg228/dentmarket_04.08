# ADR 005: единая семантика transactional outbox

## Статус

Принято.

## Контекст

Доменные сервисы записывают `OutboxEvent` в одной транзакции с изменением
агрегата. До этого решения только `PaymentCaptured` имел явный dispatcher, а
уведомления независимо сканировали события за последние семь дней. Поэтому
остальные события могли бессрочно оставаться `PENDING`, а значение статуса не
показывало, завершены ли обязательные обработчики.

## Решение

`OutboxEvent` является очередью доставки доменных событий внутри модульного
монолита. PostgreSQL остаётся durable source of truth; BullMQ только будит
worker и не владеет состоянием события.

Для каждого события dispatcher выполняет все зарегистрированные обработчики:

- wildcard-проекция уведомлений обрабатывает все типы событий и создаёт
  уведомления через детерминированный idempotency key;
- `PaymentCaptured` дополнительно создаёт по одному идемпотентному
  `ORDER_EXPORT` на каждое подходящее подключение поставщика;
- новый обработчик обязан иметь уникальное имя, явный predicate и
  идемпотентный side effect.

Событие получает `PUBLISHED` только после успеха всех подходящих обработчиков.
Отсутствие обработчика является ошибкой конфигурации и не подтверждает
доставку.

## Статусы и переходы

| Статус        | Значение                                                | Допустимый следующий статус             |
| ------------- | ------------------------------------------------------- | --------------------------------------- |
| `PENDING`     | Событие сохранено и ещё не claimed                      | `PROCESSING`                            |
| `PROCESSING`  | Один worker владеет lease                               | `PUBLISHED`, `FAILED`, `DEAD_LETTER`    |
| `FAILED`      | Retryable-ошибка; `availableAt` задаёт следующий запуск | `PROCESSING`, `DEAD_LETTER`             |
| `PUBLISHED`   | Все обязательные обработчики завершились                | финальный                               |
| `DEAD_LETTER` | Ошибка постоянная или исчерпаны попытки                 | финальный до отдельного operator replay |

Claim выполняется conditional update по `id`, предыдущему статусу и числу
попыток. Worker записывает `lockedAt`, `lockedBy` и увеличивает `attempts`.
Lease старше 60 секунд считается потерянным и может быть захвачен другим
worker. Поэтому обработчики обязаны выдерживать повторное выполнение.

## Retry и dead-letter

- стандартный лимит — 10 попыток на событие, хранится в `maxAttempts`;
- backoff: `5 секунд × 2^(attempt - 1)`, максимум один час;
- retryable-ошибка переводит событие в `FAILED` и очищает lease;
- `PermanentOutboxError` сразу переводит событие в `DEAD_LETTER`;
- последняя неуспешная попытка переводит событие в `DEAD_LETTER`;
- сообщение ошибки обрезается до 4 000 символов и сохраняется в `lastError`;
- миграция возвращает старые `PROCESSING` записи в `FAILED`, чтобы rollout не
  оставлял бесхозные claims.

## Идемпотентность

Модель доставки — at-least-once. Exactly-once между PostgreSQL и внешней
системой не обещается. Каждый side effect обязан иметь собственный уникальный
ключ:

- уведомление: `outbox:<event>:<organization>:<user>:<channel>`;
- экспорт заказа: `order-export:<order>:payment:<paymentIntent>`;
- будущий handler определяет ключ до регистрации в dispatcher.

Если один handler завершился, а следующий упал, retry повторит весь набор.
Уникальные ключи не допускают дублирования уже выполненного side effect.

## Эксплуатация

Минимальные метрики B4:

- возраст старейшего `PENDING`/`FAILED` события;
- количество `PROCESSING` с просроченным lease;
- глубина `FAILED` и `DEAD_LETTER`;
- количество попыток и ошибок по `eventType`.

Защищённый operator replay реализован в B4.3 через
`POST /api/operations/outbox/dead-letter/{eventId}/replay`. Операция требует
`operations.outbox.replay` и capability `MARKETPLACE_OPERATOR`, принимает
`idempotencyKey` и обязательную причину, а затем в Serializable-транзакции
проверяет `DEAD_LETTER`, переводит событие в `PENDING`, сбрасывает retry budget
до нуля и очищает lease/error. Payload не читается и не изменяется. Список
для оператора доступен через `GET /api/operations/outbox/dead-letter` с
ограничением `limit <= 100`; payload в ответ не выдаётся.

Каждый replay записывается в `AuditLog` с actor/organization context,
исходными попытками и причиной. `IdempotencyRecord` в scope
`outbox.dead-letter.replay` возвращает тот же результат при повторе ключа и
отклоняет reuse ключа для другого события или причины. Событие, которое уже
не находится в `DEAD_LETTER`, повторно поставить нельзя.

## Последствия

Положительные:

- `PENDING` больше не означает «событие записано, но никому не принадлежит»;
- retry, claim recovery и terminal failure одинаковы для всех типов;
- уведомления и интеграционный экспорт используют один lifecycle;
- добавление обработчика не требует нового брокера или микросервиса.

Ограничения:

- идемпотентность остаётся обязанностью каждого handler;
- долгий handler без heartbeat может быть повторно claimed после lease;
- operator replay и dashboard dead-letter остаются задачами B4.
