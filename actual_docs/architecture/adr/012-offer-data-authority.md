# ADR 012: Источник коммерческих данных предложения

## Статус

Принято владельцем 2026-09-21 в составе [Product V2 §22](../../product/DENTMARKET_PRODUCT_V2.md#22-утверждённый-состав-b2b-и-правила-кабинетов--2026-09-21).
Целевое решение; реализация и migration/contract acceptance не выполнены этой
docs-задачей. Уточняет приоритет ручных данных из ADR 004, сохраняя слой адаптеров.

## Контекст

Поставщик продаёт через несколько каналов. «10 коробок в ERP, 5 на площадке»
может означать лимит предложения, а не конфликт двух складских остатков.
Без явного источника по полю ручной ввод и очередная синхронизация незаметно
переписывают друг друга. Частое обновление браузера не устраняет эту проблему.

## Решение

- Источник задаётся по данным предложения, а не выбирается по последней записи.
  ERP ведёт физическую доступность подключённого склада; самостоятельный лимит
  площадки может её уменьшить, но не увеличить и не изменить запись ERP.
- Доступность учитывает лимит и резервы. После отражения локального резерва в ERP
  один резерв не вычитается дважды. До реализации определить в общей схеме,
  что именно сообщает адаптер (on-hand/free/reserved), единицу и версию снимка,
  что означает лимит и как учитываются ещё не отражённые внешне резервы.
  Простая формула min без этих определений не является полным контрактом.
- Цена либо поступает из выбранного ERP price list, либо управляется поставщиком
  для маркетплейса. Режим виден пользователю. Нет молчаливого last-write-wins.
- Ручной ввод/подтверждённый файл остаются источником без интеграции. Подключение
  или смена источника явно подтверждают затронутые поля. Источник и время данных
  сохраняются; поздний снимок не должен отменять более новую версию.
- Поставщик владеет коммерческими условиями своего предложения. Публичные
  canonical title/description/attributes/media проходят модерацию площадки.
  Разрешение оператору просматривать аудит не даёт право назначать цену.
- Checkout повторно проверяет условия и согласованно фиксирует резерв. Интервал
  обновления UI 60 секунд не является гарантией внешней доступности или SLA ERP.

## Совместимость и последствия

Существующие manual overrides и ADR 004 не удаляются этой задачей. Их текущий
runtime не объявляется соответствующим новому решению. При будущей реализации
нужны инвентаризация overrides, явное правило перехода/конфликта и сохранение
истории; без молчаливого изменения рабочих остатков, цен или источников.
Детали изоляции/авторизации, идемпотентности, версий и unit conversions проходят
через общую Zod-схему, API/OpenAPI/client до UI. Новые провайдеры не подключаются.

Проверки будущей реализации: 10/5 → 5, 3/5 → 3, 0/5 → 0 без резервов;
локальный резерв до/после отражения в ERP; конкурирующий checkout; устаревший
снимок; повтор сообщения; смена источника; запрет чужого tenant/offer;
несовместимые единицы; возврат/освобождение резерва. Выбранные gates — Workflow:
typecheck, tests, core contract, PostgreSQL для stock/checkout и UI critical flow.

## Отклонённые варианты

- Последняя запись всегда побеждает: скрытая потеря ручного решения/синхронизации.
- Любой manual override всегда сильнее ERP: может выставить уже проданный остаток.
- ERP полностью управляет всеми полями: не позволяет отдельный лимит площадки
  и отдельный marketplace price; подменяет общую карточку supplier description.
