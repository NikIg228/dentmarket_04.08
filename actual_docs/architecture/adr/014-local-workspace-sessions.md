# ADR 014: обычный локальный вход и сессия кабинета

Принято 22.09.2026 по утверждённым владельцем 15 исправлениям локального стенда.

Обычный dev launcher использует JWT и проверяемые сервером сессии. Development
identity headers остаются только в явно заданных изолированных API test fixtures.
Кабинеты не подставляют actor/organization; сервер подтверждает активное членство
и capability до загрузки закрытых данных. Выбор роли не меняет разрешения.

Одноразовый handoff сохраняет consumption guard и TTL. После проверки исходной
сессии и свежего членства exchange создаёт сессию кабинета с теми же методами
аутентификации и выбранной организацией. Её refresh хранится в HttpOnly cookie
целевого origin с суффиксом buyer/supplier (порты127.0.0.1 разделяют cookie jar);
refresh body содержит workspace и ожидаемый sessionId, CSRF выдаётся в ответе
и читаемой cookie path=/; HttpOnly refresh остаётся path=/api/auth.
Токены не передаются в URL. Это исключает
зависимость обновления кабинета от cookie другого поддомена и не отзывает вход
на исходном origin. Cookie в production остаётся Secure, SameSite=Lax.

Общий клиент разделяет один in-flight exchange/refresh внутри кабинета;
Web Locks сериализует refresh между вкладками поддерживающих браузеров.
Проверка
membership обязательна после загрузки сохранённой сессии. Невалидная/отозванная
сессия очищается; сетевой отказ предлагает retry и сохраняет возможность входа.
Перед запросами истекающий access token обновляется; после401 автоматически
повторяются только GET/HEAD. Неидемпотентная запись никогда не повторяется.
Потеря активного членства требует нового входа, не переключает организацию молча.

API: `GET /auth/workspaces` возвращает только активные членства текущего actor;
`POST /auth/handoff` требует текущую session identity; exchange устанавливает
cookie целевого кабинета; refresh сохраняет session/organization, CSRF и replay
guards. Контракты — workspace-session.ts, OpenAPI; тестовые правки не ослабляют
guards и не создают фиктивные юридические акцепты.

## Возврат к товару после входа — 22.09.2026

Карточка передаёт `returnTo` в страницу входа и текущую форму регистрации.
Общий валидатор допускает только `/products/{uuid}` с необязательным обратным
путём в публичный каталог. Внешние origin, fragment, другие маршруты и параметры
действий не принимаются. Подсказка навигации не является авторизацией.

`POST /auth/register` принимает необязательный `returnTo` по общей схеме
`emailRegisterSchema`; недопустимое значение отклоняется стандартным400 до
создания аккаунта. Поле входит в тип ApiClient и OpenAPI того же запроса.
Backend включает его в ссылку подтверждения email, поэтому переход не зависит
от sessionStorage исходной вкладки. Формат ответа, claim регистрации и
проверки полномочий не меняются; новая миграция не требуется.

После входа/подтверждения email handoff ведёт в выбранный товар только для
проверенного BUYER workspace. SUPPLIER открывает свой кабинет. Ошибка входа
сохраняет адрес и введённый email; обработчик не добавляет товар в корзину
и не оформляет заказ. Пока проверяется текущая сессия, кнопка добавления
недоступна. Граница этого шага — обычный вход и существующая первичная форма
регистрации, а не полная переработка onboarding/выбора кабинетов из Product§22.1.
