# Стандарт UI/UX реализации DentMarket KZ

## 1. Назначение и области применения

**Последнее решение владельца, 21.09.2026:** редизайн нужен максимально близко
к существующим визуальным референсам. После просмотра набора утверждены
компактная структура кабинетов и правила Product V2 §22. Статус:
`requirements approved; implementation not started`. Состав — §2.2; текущая
задача только фиксирует требования, runtime/visual acceptance не пройдены. Галерея,
provenance и различия вариантов — [Consolidation Standard §20](DENTMARKET_UI_UX_CONSOLIDATION_STANDARD.md#20-повторный-запрос-редизайна-и-набор-на-подтверждение-2026-09-21).
Решение отменяет ограничение будущей работы только полировкой; исторические
AUD-FIX acceptance и требования Fluent UI, доступности, API и данных сохраняются.

**Историческое решение для AUD-FIX, 15.09.2026:** сохраняем текущий дизайн,
исправляем подтверждённые UX-проблемы. Полный редизайн и референсы §2.1 не
критерий этой итерации. Задачи — [UX audit brief](AUDIT_UX_POLISH_2026-09-15.md),
очередь/чекбоксы — Foundation §8. Исторические решения ниже сохранены.

Этот стандарт задаёт качество **согласованного изменяемого интерфейса**, а не
разрешение редизайна всего проекта. Порядок работы, gates, reuse evidence и
пределы повторов — [Development Workflow](../governance/DEVELOPMENT_WORKFLOW.md).
Для docs-only задачи браузер/скриншоты не нужны. Общая UI-приёмка остаётся
B5/POST-FULL; она не запускается при каждом локальном исправлении.

DentMarket — рабочий B2B marketplace. Для клиники важны скорость поиска,
сравнения и контролируемого заказа. Для поставщика — понятное управление
каталогом, остатками и заказами. Для оператора — очередь исключений и
проверяемые решения.

Поэтому визуальное единообразие не означает одинаковые экраны:

| Поверхность                  | Система и приоритет                                                                            |
| ---------------------------- | ---------------------------------------------------------------------------------------------- |
| Buyer, Supplier, Admin       | Fluent UI v9 + `packages/ui`; ясные данные, действия, статусы, формы и таблицы                 |
| Landing и публичные страницы | существующий бренд; допускаются ограниченные принципы Taste Skill для композиции и типографики |
| Email/PDF/экспорт            | отдельные task-specific шаблоны; не переносить web-интеракции без причины                      |

Не смешивайте Fluent UI с новым design system, Tailwind-компонентами или
случайным набором иконок в рамках одного кабинета.

## 2. Базовые принципы кабинетов

1. **Состояние и действие прежде декора.** Пользователь должен за секунды
   видеть, что требует реакции, почему и что произойдёт после действия.
2. **Одна страница — одна основная задача.** Вторичные действия размещаются
   в overflow/menu, а не конкурируют с главным CTA.
3. **Термины домена едины.** «Товар» — canonical product, «предложение» —
   supplier offer. Не подменяйте их на экране.
4. **Данные объясняют происхождение.** Для цены/остатка показывайте время
   актуальности и источник там, где это влияет на решение.
5. **Необратимые действия требуют защиты.** Удаление, публикация, отмена,
   подтверждение заказа и принятие новой цены должны иметь ясные последствия
   и appropriate confirmation.

### 2.1 Глобальная навигация редизайна — решение владельца 14.09.2026

Историческое решение для полного редизайна, не требование текущей AUD-FIX
итерации: в направлении B — Quiet Editorial владелец утвердил:
**без sidebar; все ссылки на страницы находятся в верхнем header;
при прокрутке header скрывается**. Это целевое правило, не описание уже
переписанного AppShell. Исторические sidebar-checkpoints остаются evidence
прежней реализации и не назначают её повторное построение.

- Один общий header-компонент и набор tokens для всех страниц/ролей: постоянны
  геометрия, логотип, слоты поиска/навигации/действий/организации, иконки,
  типографика, отступы и контрольные состояния.
- По контексту меняются active route, организация, счётчики и разрешённые
  действия. Запрещённые роли ссылки не показываются ради визуального сходства.
  При нехватке места предлагается header-menu «Ещё»; полный реестр ссылок
  определяется route/role inventory, не пятью растровыми концептами.
- Категории и фильтры каталога — горизонтальная полоса внутри контента.
  Итог заказа рядом с таблицей — содержимое страницы, не навигационный sidebar.
- Уточнение поведения для будущего прототипа: скрывать при прокрутке вниз,
  показывать при прокрутке вверх/возврате к началу. Не скрывать во время
  открытого header-menu или focus внутри header; скрытые controls не должны
  оставаться невидимыми Tab-targets. Доступ к навигации с клавиатуры сохраняется.
  Порог, motion и mobile composition ещё проверяются на интерактивном эталоне;
  учитывать reduced motion и исключить скачки layout.
- Кардинально другая оболочка страницы или возврат боковой навигации требуют
  предварительного обсуждения и явного утверждения владельцем, до реализации.

Пять desktop-референсов и ограничения:
[Consolidation Standard §19](DENTMARKET_UI_UX_CONSOLIDATION_STANDARD.md#19-полный-редизайн-выбор-направления-2026-09-14).
Растровые картинки не заменяют общий React-компонент, WCAG/browser acceptance
и проверку фактической загрузки данных. Изменение runtime — отдельная задача.

### 2.2 Утверждённая структура кабинетов — 21.09.2026

Канонические бизнес-правила: [Product V2 §22](../product/DENTMARKET_PRODUCT_V2.md#22-утверждённый-состав-b2b-и-правила-кабинетов--2026-09-21).

| Кабинет | Основная навигация | Контекстные поверхности |
| --- | --- | --- |
| Клиника | Каталог · Заказы · Документы | Корзина/колокольчик/«Сообщения»/профиль в шапке; организация, реквизиты, сотрудники и адреса внутри настроек; списки/избранное в каталоге |
| Поставщик | Главная · Товары · Заказы · Документы | «Сообщения» в шапке; Главная — сводка продаж/заказов/задач; добавление товаров и источника из товаров; акции внутри предложения; настройки организации в профиле |
| Оператор | Задачи · Организации · Товары · Заказы · Договоры · Споры и апелляции · Аналитика | Вкладки каталога; журнал, настройки и подключения только по полномочиям; «Новая организация» — диалог реестра |

**Вход и переходы — уточнение владельца 22.09.2026.** Канонические правила и
граница реализации — [Product §22.1](../product/DENTMARKET_PRODUCT_V2.md#221-состав-и-навигация).

- Старт гостя — публичный каталог с поиском, фильтрами и карточками. После
  входа клиника сохраняет знакомый каталог с функциями своего кабинета;
  обязательная анкета новой клиники завершается перед продолжением работы.
- Авторизация и обязательный onboarding возвращают к исходному товару либо
  другому разрешённому контексту. Вход не выполняет покупку или иную
  необратимую операцию автоматически; гостевой корзины нет.
- Действующая сессия не вызывает повторный выбор роли. Обычный старт клиники —
  каталог, поставщика — главная кабинета; разрешённая прямая ссылка сохраняет
  целевой заказ, документ или другой объект.
- Тип организации выбирают при регистрации. При повторном входе сервер
  определяет доступные кабинеты по членству и правам: единственный открывается
  автоматически, выбор нужен при нескольких вариантах. Переключатель не выдаёт
  роль; операторский кабинет остаётся вне пользовательского выбора.
- «Посмотреть каталог» открывает поставщику публичный каталог с возможностью
  возврата в кабинет и сохранением сессии, без выдачи покупательских прав.
  До допуска кабинет показывает прогресс подключения и позволяет подготовить
  сведения/товары; публикация зависит от допуска организации и готовности
  предложения. Сообщения/уведомления остаются в шапке, настройки — в профиле.

Эти правила утверждены как требования. Полный UX ещё не реализован/принят;
частичные проверки входа и каталога не заменяют его приёмку. Схема URL,
объединение приложений и запуск всего редизайна этим уточнением не утверждены.

- «Предложения», «Остатки и актуальность» и «Загрузка товаров» объединяются
  под «Товары» поставщика; файл/источник выбирается в пошаговой панели.
  Публичная мастер-карточка не становится произвольно редактируемой поставщиком.
- Уточнение владельца 22.09.2026: «Сообщения» со счётчиком непрочитанных диалогов
  и контекстные кнопки из предложения/заказа. Desktop — список + диалог,
  mobile — последовательные экраны. Канонические правила —
  [Product §22.12](../product/DENTMARKET_PRODUCT_V2.md#2212-внутренние-диалоги-покупателя-и-поставщика--решение-владельца-22092026).
  Требования утверждены; реализация не начата.
- Уведомления — панель рабочих событий с переходом к объекту. Акции, снижение
  цен и новые поступления не засоряют колокольчик; маркетинговых подписок пока нет.
- Сравнение и доставка — в карточке/оформлении. AI, smart recommendations,
  тарифы и платное продвижение не входят в текущий UI. Будущие подключения не
  изображаются работающими, если нет подтверждённого обмена.
- Акции — короткая витрина + полный фильтруемый список. Для карусели обязательны
  ручное управление, пауза и остановка hover/focus; reduced motion исключает
  навязанное движение. Условия подарка видны в карточке и корзине.
- Рабочие данные показывают источник/время; обновление корзины не стирает ввод
  и не подменяет согласие с существенным изменением условий.
- Документы — самостоятельный раздел обеих сторон; договоры клиники — внутри
  архива. Поддержка и споры участника открываются из соответствующего контекста.
- Операторские инструменты каталога группируются вкладками, а не гигантской
  общей формой. Полный доступ организации не открывает операторский кабинет.
- Публичные информационные и отдельные legal-страницы отложены по решению
  владельца 21.09.2026. Исключение 22.09.2026: пустые legal-страницы общего
  договора, тарифов/правил и персональных данных создаются для supplier onboarding
  по Product §9.7; до публикации текста акцепт недоступен.

78 исходных поверхностей — исторический набор. Решение утверждает их новую
компоновку/состав, а не все точные tokens и старые варианты. Происхождение и
различия локальных фильтров каталога из §20 Consolidation Standard сохраняются;
§2.1 не используется для молчаливого выбора спорного варианта.

## 3. Обязательные состояния

Каждая data-driven область обязана иметь все применимые состояния:

- **Loading:** skeleton или progress с сохранением layout; не «прыгающий» экран.
- **Empty:** причина отсутствия данных и следующий полезный шаг.
- **Error:** человеческое объяснение, retry/action и технический `requestId`,
  если он доступен; не раскрывать stack trace.
- **Success:** feedback после сохранения, публикации или импорта.
- **Stale/conflict:** показывать, что данные изменились, старое → новое
  значение и выбор пользователя. Для корзины это обязательный reprice diff.
- **Permission denied:** объяснять недостаток права без имитации пустого списка.

## 4. Формы и рабочие таблицы

- Используйте стандартные Fluent controls и единые tokens; label всегда
  видим, placeholder не заменяет label.
- Для исправляемых форм по запросу владельца — статичная иконка «?» у label
  с коротким «что это и зачем», доступная hover/click/keyboard/touch.
  Критические ограничения остаются видимыми вне tooltip. Внедрение по
  AUD-FIX-08 не считается уже выполненным на всех существующих полях.
- Ошибка показывается рядом с полем и понятна без цвета. Focus order и
  submit доступны с клавиатуры.
- При server validation сохраняйте введённые значения. Блокируйте повторный
  submit, пока запрос в работе, но давайте понятный feedback.
- В таблицах сначала выводите поля, по которым принимают решение. Статус не
  должен быть единственным способом понять проблему: добавляйте текст/tooltip.
- Фильтры, сортировка и pagination должны быть явными и не сбрасывать контекст
  после одного действия без необходимости.
- На мобильном экране таблица либо имеет осмысленный horizontal scroll с
  закреплённым ключевым контекстом, либо переходит в карточки. Нельзя просто
  уменьшать текст до нечитаемого размера.

## 5. Адаптивность и доступность

- Проверяйте минимум desktop и 390 px viewport для изменённого critical flow.
- Не допускайте горизонтального overflow страницы, обрезанных CTA и
  hover-only действий.
- Контраст текста и controls соответствует WCAG AA; цвет не единственный
  носитель статуса; focus indicator сохраняется.
- Dialog, menu, drawer и toast работают с клавиатурой и screen reader.
- Закрытый mobile drawer исключён из последовательности `Tab`; при открытии
  фокус переходит на доступное действие закрытия, `Escape` закрывает drawer и
  возвращает фокус на кнопку открытия.
- Motion не должна блокировать действие; учитывайте `prefers-reduced-motion`.

## 6. Landing и Taste Skill: ограниченное применение

Внешний проект `Leonxlnx/taste-skill` полезен как набор anti-generic правил
для landing: сначала brief, затем намеренная композиция, иерархия, ритм,
типографика и осмысленная motion. Он не является design system DentMarket и
сам не предназначен для dense dashboards, data tables и multi-step forms.

Перед изменением публичной страницы зафиксируйте:

```md
Brief: аудитория и одно главное действие.
Art direction: 2–3 визуальных принципа, совместимых с брендом.
Density/motion: осознанный уровень и reduced-motion fallback.
Preservation: что нельзя менять — URL, IA, SEO, copy, analytics events.
```

Не копируйте текст, код, assets или «жёсткие» эстетические запреты из чужого
skill-файла как универсальное правило. Для существующего сайта сначала
сверьте изменяемую поверхность и уже доступный audit/evidence; новый полный
аудит не обязателен для каждого fix. Затем применяйте необходимые изменения: типографика,
spacing, tokens, компоненты, только после этого — новая композиция.

## 7. Definition of Done для UI-задачи

- [ ] Пользовательский сценарий и primary action ясны.
- [ ] Реализованы нужные loading/empty/error/success/conflict состояния.
- [ ] Проверены keyboard, focus и desktop/mobile layout.
- [ ] Использованы общий Fluent UI / `packages/ui`, без второго design system.
- [ ] Состояния и ограничения backend не замаскированы оптимистичным UI.
- [ ] Добавлен или обновлён unit/e2e test для критического поведения.
- [ ] Выполнены команды из `../governance/DEVELOPMENT_WORKFLOW.md`.

Чек-лист применяется к scope текущей карточки. После принятия результата не
создавайте дополнительные варианты ради «ещё лучше» и не запускайте новый
цикл скриншотов без изменения UI/данных/viewport, влияющего на проверку.
Проблема API/входа/fixtures фиксируется отдельно: error-state smoke не считается
populated-data acceptance, но и не требует нового дизайна работающего компонента.
