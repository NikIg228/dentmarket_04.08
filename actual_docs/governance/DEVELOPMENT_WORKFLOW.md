# Workflow разработки DentMarket KZ

## 1. Цель

Каждая задача должна давать проверяемое изменение одного пользовательского
сценария или технического инварианта. Этот workflow не разрешает «код ради
кода»: до реализации известны граница, риск и критерий готовности.

Версия правил: 2026-09-14. Этот документ — единственное место для матрицы
проверок, лимитов повторов и execution evidence. Product/Foundation определяют
результат и очередь; UI standards — свойства интерфейса; ADR/runbooks —
архитектуру и конкретные процедуры. Их списки команд не суммируются механически.
Обязательные safety-инварианты не ослабляются ради экономии запусков.

Решение владельца 2026-09-21: единственная writable source folder —
`C:\Users\user\Desktop\dentmarket-kz-main`, один активный writer на весь репозиторий.
Не создавать другие worktrees/клоны для кода; старые деревья только read-only.
Перед правками сверять корень/HEAD/dirty files/владельца согласно AGENTS.md.
Изоляция тестовых данных/портов сохраняется; она не требует второй копии исходников.

## 2. Карточка задачи

Перед кодом задача должна содержать:

```md
## ID / название / основание

ID существующего пункта или явный запрос пользователя; короткий результат.
Тип: docs-only / analysis / code / environment / release. Не путать их DoD.

## Контекст и scope

Кто использует; какой Product V2 сценарий затрагивается; что сознательно не
делаем.
Существующий code path/test/evidence; конкретный пробел; разрешённые файлы/области.

## Поведение

Given / When / Then для happy path, ошибки и границы доступа.

## Контракт и данные

Маршруты/схемы, сущности, migration, audit/outbox, идемпотентность и
совместимость — только если применимо.

## UI/UX

Экран, состояния loading/empty/error, desktop/mobile, доступность.

## DoD

Точные тесты и verification-команды. `[ ]` превращается в `[x]` только после
фактического успешного запуска.

## Execution budget / checkpoint

Профиль, рабочий checkout, test DB alias (без секрета), fixtures и owned процессы.
Список обязательных gates, reusable evidence, timeouts и причины rerun.
Лимит: первичная попытка + 2; блокер, число попыток и один следующий шаг при stop.
```

Если неизвестно хотя бы одно из: владелец данных, tenant boundary, пользователь
результата или критерий успеха, остановитесь на анализе и уточните задачу.
Если запрос уже однозначен, коротко зафиксируйте карточку и выполняйте его без
ещё одного круга согласования. Новая карточка не является разрешением новой функции.

## 3. Последовательность реализации

1. **Разобраться.** Прочитать [AGENTS.md](../../AGENTS.md), целевой документ и релевантный
   код. Проверить текущее дерево Git.
2. **Спроектировать.** Согласовать task card. Для сложного, необратимого или
   cross-cutting решения создать ADR до реализации.
3. **Построить контракт.** Сначала schemas/OpenAPI/api-client, если меняется
   публичный API; затем server; затем UI.
4. **Реализовать минимально.** Не совмещать чистку старого кода и новую
   бизнес-функцию, если они не необходимы друг другу.
5. **Проверить риск.** Добавить test/regression gate, который воспроизводит
   именно риск задачи.
6. **Проверить интеграцию.** Выполнить матрицу ниже, обновить docs и
   проверить diff.
7. **Завершить.** Зафиксировать evidence; после обязательных gates выполнить
   commit и немедленный push по постоянному разрешению владельца (§5.1).
   Проверить публикацию/CI и остановиться на DoD, не начинать новую задачу.

Нельзя автоматически продолжать старый список запросов, заново реализовывать
проверенный slice или чинить все найденные смежные дефекты. Для предложения
сохраните один пункт с основанием и границей в существующем источнике правды.
Новая фаза — только если она входит в явно разрешённую последовательность.

## 4. Матрица проверок

| Изменение                          | Обязательно                                       | При необходимости                                                  |
| ---------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------ |
| Docs-only / аудит правил           | Локальные ссылки, согласованность, сохранность чужих изменений/истории, `git diff --check` | Проверка упомянутых npm scripts без их запуска; runtime suites не требуются |
| Read-only анализ                  | Целевая сверка исходников/evidence, без изменений | Воспроизведение конкретной гипотезы, если безопасно и необходимо; не все gates |
| Любой TS-код                       | `npm run typecheck`, `npm test`, `git diff --check` | `npm run build` для изменённого приложения                            |
| Core API contract                  | `npm run verify:core-contract`                       | `npm run verify:pilot-backend` для полного purchase flow              |
| Prisma/checkout/tenant/idempotency | `npm run verify:postgres`                            | migration на чистой локальной БД                                   |
| API/worker composition             | `npm run verify:runtime-split`                       | Config gate, если затронуты environment rules |
| Production environment rules       | `npm run verify:production-config`                   | Runtime/transport/storage gate по конкретной границе |
| Общий deployment profile / frontend composition | `npm run verify:frontend-profile`, `npm run verify:pilot-composition`, четыре web build, `npm run verify:web` в pilot | Для активации полного профиля также go_live smoke изменённых поверхностей; pilot E2E не заменяет его |
| Local launcher / full-feature demo | `npm run verify:local-profile`, затронутые profile gates и smoke целевого запуска | Общий профиль затронут — строка выше; отдельный launcher не требует нового бизнес-функционала |
| Buyer/Supplier/Admin critical UI   | TS минимум, regression, build затронутых приложений, `npm run verify:web`, keyboard/mobile smoke изменённого flow | Более широкая visual/accessibility matrix при изменении shared tokens/shell, не для каждого текста |
| Landing/public UI                  | typecheck + build приложения                      | Lighthouse/visual review, если меняется performance-critical экран |
| Security/file/integration          | целевой `verify:*` сценарий                       | `npm audit --omit=dev --audit-level=high`                             |
| Release candidate                  | `npm run verify:release`                             | `docker compose config --quiet`                                    |

`npm run verify:web` и API verification scripts требуют подготовленного local
окружения. Не скрывайте этот факт: если окружение не было поднято, укажите
проверку как не выполненную.

Матрица выбирает проверки **по изменению**, а не по названию папки: правка
описания checkout не запускает PostgreSQL, изменение checkout-транзакции —
запускает обязательно. Для нового public contract требуются schema/client
regressions; purchase contract дополнительно verify:core-contract. Полный
CORE-09 и release сохраняют свои обязательные наборы, но не выполняются на
каждом подпункте. Новый риск может добавить gate в карточку до запуска;
удалять/ослаблять упавшую проверку для получения pass запрещено.

### 4.1 Preflight до дорогих запусков

1. Один раз зафиксировать branch/HEAD и dirty paths; чужие изменения сохранить.
   Чтение начинать с известных маршрутов/`rg`; не сканировать весь репозиторий
   заново после каждого результата. После двух уточнений без новых данных
   зафиксировать, чего не хватает, вместо бесконечных вариантов одного поиска.
2. Проверить scripts и их зависимости: многие verify aliases повторно собирают
   API/schemas; verify:release уже включает typecheck/test/build. Составить один
   execution plan, а не запускать каждый список из каждого документа.
3. Выбрать профиль и один режим сервера: dev либо production artifacts.
   Не запускать Next dev/build/typegen одновременно для одной `.next` директории.
   Не использовать pilot artifact для go_live. Указать API URL и способ входа;
   не считать смонтированную панель доказательством загрузки её данных.
4. Проверить health, identity/permissions и требуемую свежесть fixtures до E2E.
   DB alias, порт, назначение и cleanup должны быть известны. DATABASE_URL из
   окружающей shell сам по себе не доказывает, что БД disposable.
5. Использовать уже предназначенную test DB. Новая временная БД допустима как
   оговорённая часть test setup с проверкой точной цели; не выдавать CREATEDB,
   не менять public extensions, не клонировать рабочую БД и не поднимать новый
   PostgreSQL cluster автоматически после ошибки. Такой переход требует
   отдельного согласования. Stale fixtures — проблема test setup, не основание
   отключить freshness или reseed рабочий каталог.
6. Для task-specific runtime отключить необязательные внешние side effects
   штатными test adapters/config, не отключая проверяемые guards. Команды,
   которые могут записывать данные, запускать только в оговорённой среде.

### 4.2 Реестр запусков и переиспользование pass

Для дорогих gates хранить краткую запись в карточке/Acceptance Matrix или
связанном ignored evidence artifact, не заводить новый параллельный backlog:

| Gate | Входы | Команда / artifact | Попытка / причина | Исход / длительность |
| --- | --- | --- | --- | --- |
| Точное имя | HEAD + relevant dirty diff/hash, lockfile, toolchain, profile, test/config и DB/fixture revision | Реальная команда, лог/trace | 1; или конкретное изменение/гипотеза | PASS / FAIL / BLOCKED / NOT_RUN / REUSED_PASS |

Для грязного дерева одного HEAD недостаточно. Не хранить секретные env values;
при изменении конфигурации записывать имена параметров и безопасную revision.
Существующий PASS можно засчитать как REUSED_PASS, только если проверяемые
исходники, зависимости, tests/config, artifact, профиль и значимое состояние
данных не изменились и исходный результат доступен. Новый checkout без такой
связи требует проверки. Наличие старой галочки само по себе недостаточно.

Изменение docs-only/комментария отчёта, чтение логов, новый чат или commit
не инвалидируют runtime evidence неизменённых входов. Изменение схемы/lockfile,
значимых env/данных или потерянный artifact инвалидируют соответствующие gates.
Повторять нужно затронутые проверки, не весь проект по умолчанию. Повторный
осознанный freshness/load/security scan выполняется по своему scope и новым входам.

Одна общая сборка может обслуживать несколько gates на одной revision.
Прямой запуск underlying script разрешён только после чтения npm alias,
выполнения **всех** его prerequisite шагов и записи эквивалентного покрытия.
Нельзя заменить compose gate на health, PostgreSQL на mocks, полный flow на
contract-only или production build на dev compile. Если эквивалентность
не доказана, используется alias. Turbo cache допустим при корректных ключах;
`--force`/очистка cache — только по конкретному подозрению или требованию gate.

### 4.3 Ограниченные повторы и время

- Максимум 3 попытки на один gate/блокер: первичная + 2 повторных. Перед повтором
  записать причину, изменение входов или проверяемую новую гипотезу. Без изменений
  допустим один retry лишь при наблюдаемой transient ошибке, не при assertion fail.
- Две одинаковые ошибки без нового проверяемого основания → остановка раньше
  лимита. Нельзя перебирать браузеры, shell, профили и новые чаты ради сброса
  счётчика; допустим один обоснованный fallback в рамках общего лимита и правил tool.
- После 3 неудач остановить затронутую фазу: сохранить ошибку, попытки, выполненную
  диагностику и один следующий шаг. Продолжение — новое явное решение пользователя
  с изменённой предпосылкой/планом, не автоматический цикл. Не заявлять pass.
- В карточке до запуска задать wall-clock budget. Defaults при отсутствии
  специального runbook: probe 2 минуты, запуск сервера 5 минут, отдельная
  build/test команда 20 минут, полный suite 45 минут; диагностика одного блокера
  не более 15 минут суммарно. Более длинный soak/scan имеет заранее выбранный
  finite budget из разрешённой задачи/skill. Не повышать timeout после каждой ошибки.
- Работающий процесс с session/job ID не запускать вторым экземпляром.
  Ожидать через штатный wait/poll, обычно 15–30 секунд, не блокируя общение более
  60 секунд. Отсутствие новых логов не равно зависанию: учитываются исходный
  budget и состояние процесса. Poll не новая попытка, restart — новая.
- Встроенные retries test runner не скрывать: flaky pass указывается отдельно
  и оценивается по риску. Этот execution budget не меняет retry-настройки CI,
  бизнес-очередей или provider SDK и не является установленным OS kill-switch.
- По истечении budget остановить только свой процесс/дерево безопасным способом,
  сохранить partial result и отметить TIMEOUT/BLOCKED, не SUCCESS.

### 4.4 Ошибка окружения, завершение и checkpoint

Классифицировать сбой: код/assertion; данные/конфигурация; инструмент/runtime;
нет разрешения/внешней зависимости. Исправление приложения допускается только
при evidence его дефекта в текущем scope. Missing plugin, browser data-URL
error, permission profile, stale fixture и занятый порт не являются основанием
переписывать бизнес-логику. Не обходить отказ безопасности через другой инструмент.

При PASS всех выбранных gates: обновить чекбоксы, оформить результат и остановиться.
При обязательном FAIL/BLOCKED: оставить пункт открытым, не начинать следующую фазу.
Сохранять branch/dirty scope, принятые решения, результаты/попытки, owned процессы,
следующее действие. Новый контекст продолжает checkpoint после проверки изменений,
а не повторяет подготовку с нуля. Этот журнал не заменяет продуктовые статусы.

Останавливать только созданные исполнителем сервисы, закрывать свои временные
вкладки, убирать тестовую browser identity и viewport overrides. Чужие серверы,
БД и данные не трогать. Невозможный cleanup честно указать; для удаления/переноса
проверить абсолютный target, при неясном происхождении запросить направление.

## 5. Review перед коммитом

- [ ] Изменение соответствует Product V2 и не включает скрытый scope creep.
- [ ] Нет нарушения tenant isolation, authorization или денежной точности.
- [ ] У write-операций определены validation, conflict и idempotency semantics.
- [ ] У интерфейса есть loading, empty, error и disabled/submitting state.
- [ ] Тест покрывает изменённое правило или regression.
- [ ] Контракт, OpenAPI, api-client и UI согласованы, если API менялся.
- [ ] Миграции и seed не смешивают demo/test/pilot данные без решения.
- [ ] Документация обновлена или явно не требует обновления.
- [ ] `git diff --check` прошёл; в diff нет секретов и случайных generated files.

### 5.1 Commit и немедленный push после проверенной задачи

Решение владельца 2026-09-21 является постоянным разрешением на commit/push
завершённой согласованной реализации, включая документацию. Не нужен отдельный
вопрос после каждой задачи. Read-only, явное «без push» и safety-блокеры имеют
приоритет. Это правило поведения агента, не фоновый Git-hook.

1. Подтвердить единственную папку из AGENTS.md, одного writer, ветку/HEAD и
   согласованные remote/target branch. Если upstream не определён или неоднозначен,
   запросить одно решение, не назначать main автоматически.
2. Пройти требуемые gates либо доказать REUSED_PASS неизменённых входов.
   Review распространяется на staged diff и все outgoing commits, не только
   последний файл. Не включать секреты, данные клиентов, случайные generated
   файлы, чужой или непроверенный WIP. Stage — явные проверенные пути/hunks.
3. Создать осмысленный conventional commit. Fetch целевого remote, убедиться
   в возможности fast-forward. Расхождение/несвязанная история — блокер;
   не делать скрытый merge/rebase, reset, force-push или смену грязной ветки.
4. Немедленно выполнить обычный push в согласованную ветку. Прочитать remote
   SHA и сравнить с отправленным local HEAD. При ошибке сохранить commit;
   задача имеет статус «локально закоммичено, публикация заблокирована».
5. Отдельно проверить применимый CI: pending/NOT_RUN не равны PASS. В отчёте
   дать папку, commit/ветку, проверки, фактические push и CI. Не объявлять
   полностью завершённой доставку с непройденным обязательным gate.

До первого push в новую цель проверить автоматические эффекты CI/CD;
неожиданное развёртывание требует решения владельца. Разрешение не включает
создание PR, release/tag/deploy, изменения рабочей БД или начало следующей фазы.
Сжатие контекста и чужие правки не являются поводом автоматически коммитить.

## 6. Правило документации

Актуальная последовательность и чекбоксы ведутся в Backend Foundation;
Acceptance Matrix хранит evidence, Product V2 — требования. Не создавать
параллельное ТЗ для повторения тех же задач. Завершённая фаза переносится в
историю с датой, revision, командами и ограничениями; её regression tests
остаются в risk-based gates; это не требование запускать их при любой правке docs.
Смешанный старый план архивируется только с реестром
переноса всех применимых незавершённых пунктов. Отложенное не отмечается X.

Решение 2026-09-14 откладывает объединённую приёмку POST-FULL до готовности
backend и frontend, а POST-BE — до готовности backend. Это не отменяет
unit/integration/contract и затронутые browser/security gates каждой фазы.
При красном обязательном gate фаза останавливается; следующую не начинать.
Docs-only задача проверяет ссылки, сохранность истории и diff; она не
повышает статусы runtime readiness и не требует имитировать запуск TS-тестов.

Обновляйте документ в той же задаче, если изменился:

- продуктовый scope или обязательное бизнес-правило —
  `../product/DENTMARKET_PRODUCT_V2.md`;
- последовательность реализации/DoD —
  `../backend/DENTMARKET_BACKEND_FOUNDATION_V2.md`;
- архитектурный trade-off — новый файл в `../architecture/adr/`;
- команда запуска/операционный процесс — соответствующий runbook;
- пользовательский UI contract —
  `../ui-ux/UI_UX_IMPLEMENTATION_STANDARD.md` только
  если это новое общее правило, а не частный дизайн страницы.

## 7. Финальный отчёт

Исполнитель завершает задачу кратко: результат, затронутые границы,
проверки и их исход, известные ограничения, commit/branch. Нельзя заменять
фактический результат формулировкой «должно работать».

Не писать «всё зелёное», если обязательный gate не пройден; отличать свежий
PASS, REUSED_PASS, неполную проверку и NOT_RUN с причиной. Указать применённые
роли/skills и причину выбора. Для реализации действует постоянное разрешение
§5.1; для read-only не создавать commit только ради шаблона отчёта.

## Сохранение контекста и передача задачи (2026-09-19)

Эти правила сохраняют ход работы, но не создают новую очередь разработки.
Возраст задачи и число сжатий сами по себе не доказывают ошибку модели и не
являются основанием переписывать код или заново выполнять завершённые пункты.

### Начало и восстановление

1. До изменений прочитать актуальный корневой AGENTS.md, профильный источник
   требований и checkpoint именно выбранной задачи. После сжатия/возобновления
   повторно сверить их с последним запросом пользователя.
2. Проверить фактические cwd, repository root, branch, HEAD и dirty paths;
   отделить прежние пользовательские изменения от собственных. Worktree и
   ветка из старой сводки не считаются текущими без проверки.
3. Восстановить один разрешённый результат, критерии приёмки, владельца и
   следующий шаг. Не продолжать все исторические «продолжай» и весь backlog.
   Если задачи несколько и выбор неоднозначен, уточнить выбор, не брать самую
   свежую запись автоматически.
4. Сопоставить ожидаемый результат с существующими кодом и evidence. Не
   реализовывать уже сделанное заново; выяснить конкретный оставшийся пробел.
   Несовпадение требований и кода записать как расхождение, не менять требования
   ради соответствия коду.
5. После передачи в новую задачу кратко подтвердить понимание: продукт и цель,
   разрешённый scope, что доказанно сделано, что не проверено, блокер и следующий
   шаг. Это сверка с файлами, не пересказ всей истории.

### Checkpoint без напоминаний пользователя

- Для многошаговой работы поддерживать одну компактную запись на задачу.
  Сначала использовать существующую карточку и evidence; не плодить копии.
- Обновлять её после завершённого смыслового этапа, существенного решения,
  проверки или появления блокера, а также перед финальным ответом/известной
  передачей. Не ждать 100% заполнения контекста. Нельзя гарантировать запись
  непосредственно перед внезапным прерыванием или автоматическим сжатием.
- Короткому ответу без изменений отдельный файл не нужен. Если запрос строго
  read-only, файловые записи запрещены: checkpoint дать в ответе либо сохранить
  только в отдельно разрешённом реестре.
- Фиксировать подтверждённые решения отдельно от предложений и неизвестного.
  Не включать полные переписки, секреты, персональные данные и сырые дампы.
- Не редактировать карточку другого активного исполнителя. Один scope,
  включая API-контракт и общий документ, имеет одного владельца; отдельные
  worktrees сами по себе не устраняют смысловые конфликты.

Минимальная запись:

```md
# <ID существующей задачи или короткий уникальный ID> — <результат>
Обновлено: <дата/время/часовой пояс>
Владелец: <task/thread ID, если доступен; иначе явно неизвестен>
Состояние: active / blocked / ready-for-handoff / closed
Основание: <актуальный запрос; ссылки на канонические требования>
Цель / DoD / разрешённые области / что не делаем:
Checkout / branch / HEAD:
Dirty paths: <свои / чужие / происхождение не установлено>
Выполнено: <конкретный результат + файл/commit/evidence>
Реализовано, но не проверено:
Интегрировано в целевую ветку: <доказательство или нет/неизвестно>
Развёрнуто и проверено в среде: <какой или нет/неизвестно>
Проверки: <команда, дата, входы: HEAD + relevant diff/hash,
           профиль/fixtures/dependencies, PASS/FAIL/BLOCKED/NOT_RUN,
           ссылка на доступный результат>
Блокер / попытки / уже отвергнутые гипотезы:
Принятые решения: <кто утвердил и где>
Незавершённое в текущем scope:
Собственные процессы / артефакты: <ID/пути или нет>
Следующий шаг: <одно конкретное действие>
Условие остановки:
```

Статус «реализовано» не означает «проверено», «интегрировано» или
«развёрнуто». Процент готовности без фиксированного списка критериев не
указывать. Новый чат не сбрасывает счётчик неудачных попыток. Проверенный
результат переиспользовать только при доступном evidence и неизменных
значимых входах; смена чата сама по себе не требует полного rerun.

### Передача и остановка

- При достигнутом DoD сохранить evidence, закрыть только подтверждённый пункт
  в каноническом реестре и остановиться. Новые улучшения — предложения, не
  автоматические поручения.
- При смене задачи подготовить checkpoint и короткое задание-продолжение:
  точный путь к записи, разрешённый scope, DoD и следующий шаг. Передавать
  ссылки на источники, а не только пересказ истории.
- Прежде чем передать исполнение, подтвердить остановку прежнего владельца.
  Преемник сначала читает запись и сверяет Git/evidence; только затем продолжает.
  Архивация допустима после подтверждения передачи, не вместо неё.
- Не создавать/архивировать задачи, не коммитить, не пушить, не переносить
  worktrees и не удалять файлы только потому, что произошло сжатие.
  Такие действия требуют соответствующего запроса/разрешения.
- Автоматическое напоминание не является блокировкой конкурентной записи,
  доказательством выполнения правил или автоматическим сохранением сводки.

Для DentMarket / Platforma.Market требования остаются в Product V2,
очередь — в Backend Foundation, evidence — в Acceptance Matrix (§1 AGENTS.md).
Сохранять checkpoint в существующей карточке; при её отсутствии —
`actual_docs/governance/task-state/<task-id>.md`. Это состояние исполнения,
не второй backlog. Матрица проверок и лимиты §4 остаются без изменений.

### Подключение к Codex

В `.codex/hooks.json` подготовлены напоминания для `SessionStart`
(startup/resume/clear/compact) и `UserPromptSubmit`. Команды только выводят
короткую инструкцию: они не читают переписку, не пишут файлы, не вызывают AI
и не управляют Git или задачами. Смысловую запись ведёт исполнитель по правилам
выше; это не гарантия checkpoint перед каждым сжатием.

Hooks требуют доверия к проекту и отдельного review/trust определения в Codex
(официальный CLI: `/hooks`). Не обходить trust и не включать его через правку
служебных хранилищ. После установки/изменения проверить загрузку в новой сессии;
пока фактический запуск не подтверждён, статус автоматизации — «не проверено».
Уже открытые задачи и отдельные worktrees не считать автоматически обновлёнными.
В другом worktree код не менять: продолжать только в канонической папке из
AGENTS.md после сверки владельца. Не переносить hooks в старые деревья и не
менять их trust автоматически.

Источник механизма: https://learn.chatgpt.com/docs/hooks
