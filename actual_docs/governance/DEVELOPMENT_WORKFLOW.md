# Workflow разработки DentMarket KZ

## 1. Цель

Каждая задача должна давать проверяемое изменение одного пользовательского
сценария или технического инварианта. Этот workflow не разрешает «код ради
кода»: до реализации известны граница, риск и критерий готовности.

## 2. Карточка задачи

Перед кодом задача должна содержать:

```md
## Название

Короткое действие и пользовательский результат.

## Контекст и scope

Кто использует; какой Product V2 сценарий затрагивается; что сознательно не
делаем.

## Поведение

Given / When / Then для happy path, ошибки и границы доступа.

## Контракт и данные

Маршруты/схемы, сущности, migration, audit/outbox, идемпотентность и
совместимость — только если применимо.

## UI/UX

Экран, состояния loading/empty/error, desktop/mobile, доступность.

## DoD

Точные тесты и verification-команды. `[ ]` превращается в `[x]` только после
фактического успешного запуска.
```

Если неизвестно хотя бы одно из: владелец данных, tenant boundary, пользователь
результата или критерий успеха, остановитесь на анализе и уточните задачу.

## 3. Последовательность реализации

1. **Разобраться.** Прочитать `../../AGENTS.md`, целевой документ и релевантный
   код. Проверить текущее дерево Git.
2. **Спроектировать.** Согласовать task card. Для сложного, необратимого или
   cross-cutting решения создать ADR до реализации.
3. **Построить контракт.** Сначала schemas/OpenAPI/api-client, если меняется
   публичный API; затем server; затем UI.
4. **Реализовать минимально.** Не совмещать чистку старого кода и новую
   бизнес-функцию, если они не необходимы друг другу.
5. **Проверить риск.** Добавить test/regression gate, который воспроизводит
   именно риск задачи.
6. **Проверить интеграцию.** Выполнить матрицу ниже, обновить docs и
   проверить diff.
7. **Зафиксировать.** Сделать один логичный commit и push только после
   успешной локальной проверки.

## 4. Матрица проверок

| Изменение                          | Обязательно                                       | При необходимости                                                  |
| ---------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------ |
| Любой TS-код                       | `pnpm typecheck`, `pnpm test`, `git diff --check` | `pnpm build` для изменённого приложения                            |
| Core API contract                  | `pnpm verify:core-contract`                       | `pnpm verify:pilot-backend` для полного purchase flow              |
| Prisma/checkout/tenant/idempotency | `pnpm verify:postgres`                            | migration на чистой локальной БД                                   |
| API/worker/config                  | `pnpm verify:runtime-split`                       | `pnpm verify:production-config`                                    |
| Buyer/Supplier/Admin critical UI   | typecheck + relevant unit test                    | `pnpm verify:web` и ручной keyboard/mobile smoke                   |
| Landing/public UI                  | typecheck + build приложения                      | Lighthouse/visual review, если меняется performance-critical экран |
| Security/file/integration          | целевой `verify:*` сценарий                       | `pnpm audit --prod --audit-level high`                             |
| Release candidate                  | `pnpm verify:release`                             | `docker compose config --quiet`                                    |

`pnpm verify:web` и API verification scripts требуют подготовленного local
окружения. Не скрывайте этот факт: если окружение не было поднято, укажите
проверку как не выполненную.

## 5. Review перед коммитом

- [ ] Изменение соответствует Product V2 и не включает скрытый scope creep.
- [ ] Нет нарушения tenant isolation, authorization или денежной точности.
- [ ] У write-операций определены validation, conflict и idempotency semantics.
- [ ] У интерфейса есть loading, empty, error и disabled/submitting state.
- [ ] Тест покрывает изменённое правило или regression.
- [ ] Контракт, OpenAPI, api-client и UI согласованы, если API менялся.
- [ ] Миграции и seed не смешивают demo/test/pilot данные без решения.
- [ ] Документация обновлена или явно не требует обновления.
- [ ] `git diff --check` прошёл; в diff нет секретов и случайных generated files.

## 6. Правило документации

Обновляйте документ в той же задаче, если изменился:

- продуктовый scope или обязательное бизнес-правило —
  `../product/DENTMARKET_PRODUCT_V2.md`;
- последовательность реализации/DoD —
  `../backend/DENTMARKET_BACKEND_FOUNDATION_V2.md`;
- архитектурный trade-off — новый файл в `../architecture/adr/`;
- команда запуска/операционный процесс — соответствующий runbook;
- пользовательский UI contract —
  `../ui-ux/UI_UX_IMPLEMENTATION_STANDARD.md` только
  если это новое общее правило, а не частный дизайн страницы.

## 7. Финальный отчёт

Исполнитель завершает задачу в пяти строках: результат, затронутые границы,
проверки и их исход, известные ограничения, commit/branch. Нельзя заменять
фактический результат формулировкой «должно работать».
